# 戦闘の保存失敗から再起動しても戻れない問題 (2026-10-30)

## 確認できたこと

- 本番のゲスト認証・規約同意・claim・検証用の一括戦闘(turn)はHTTP 200だった。検証用アカウントは削除済み。戦闘の応答は約1.5秒で、毎行動の通信待ちは残る。
- 利用者のアカウントの要求内容・本番の実行ログは取得していないため、最初の失敗が回線・サーバー例外・容量制限のどれかは確定していない。
- 要求は送信前に端末へ永続化され、再起動時も同じ要求をrecoverする。毎回同じ内容で失敗する要求には退避手段がなく、再起動しても再接続画面から出られない経路がある。
- fetchJSONはHTTP状態の検査前にJSONを解析していた。413など空のエラー応答では解析例外となり、元のHTTP状態を失っていた。失敗画面も原因を区別しなかった。
- 一時的な通信エラーでも直ちに全画面の手動再接続待ちになっていた。

## 修正

- 一時障害のみ同じ要求ID・内容で最大3回自動再送する。400/401/403/409/413は自動再送の対象にしない。
- 空のHTTPエラーでも状態番号を保持し、失敗画面に表示する。関数の失敗には問い合わせ番号を付け、サーバーログと照合できるようにする。セーブ・認証情報はログへ出さない。
- 送信待ちがある場合、失敗画面から明示的に「保存済みの記録から再開」できる。元の要求を端末の`:recovery`へ保管してから送信待ちを解除し、再起動してサーバーの確定済み記録を取得する。保管に失敗したら元の要求は残す。未確定の操作が反映されない場合があることを操作前に説明する。
- 戦闘の結果・次手番の確定、重複実行の防止、通常の返答喪失時の自動回収は維持する。

## 検証

- `node tools/cloud/check.mjs`: 既存の戦闘・乱数・再送検証に、自動再送・空HTTPエラー・恒久エラー・退避失敗時の保護を追加。
- `python3 tools/cloud/recovery-browser.py`: 再起動後も同じ要求が失敗する状況を再現し、実際の復旧ボタンで退避しサーバーの記録から再開。
- `python3 tools/cloud/unobtrusive-browser.py`: 通常保存中の操作・自動移動・戦闘待ち・失敗からの再接続。
- `node tools/cloud/database-check.mjs <PGlite>`: 実際のSQLとAPIの再送・確定状態・競合。
- `node tools/cloud/deploy-check.mjs`: 接続設定・権限・公開時の検査。
