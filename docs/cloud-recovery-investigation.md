# 戦闘の保存失敗から再起動しても戻れない問題 (2026-10-30)

## 確認できたこと

- 本番のゲスト認証・規約同意・claim・検証用の一括戦闘(turn)はHTTP 200だった。検証用アカウントは削除済み。戦闘の応答は約1.5秒で、毎行動の通信待ちは残る。
- 利用者のアカウントの要求内容・本番の実行ログは取得していないため、最初の失敗が回線・サーバー例外・容量制限のどれかは確定していない。
- 要求は送信前に端末へ永続化され、再起動時も同じ要求をrecoverする。毎回同じ内容で失敗する要求には退避手段がなく、再起動しても再接続画面から出られない経路がある。
- fetchJSONはHTTP状態の検査前にJSONを解析していた。413など空のエラー応答では解析例外となり、元のHTTP状態を失っていた。失敗画面も原因を区別しなかった。
- 一時的な通信エラーでも直ちに全画面の手動再接続待ちになっていた。

## 修正

- 一時障害のみ同じ要求ID・内容で最大3回自動再送する。400/401/403/409/413は自動再送の対象にしない。
- 空のHTTPエラーでも状態番号を保持し、失敗画面に表示する。関数の失敗には問い合わせ番号を付け、サーバーログと照合できるようにする。セーブ・認証情報はログへ出さない。
- 送信待ちがある場合、失敗画面から明示的に「保存済みの記録から再開」できる。元の要求を端末の`:recovery`へ保管してから送信待ちを解除し、再起動してサーバーの確定済み記録を取得する。保管に失敗したら元の要求は残す。未確定の操作が反映されない場合があることを操作前に説明する。
- 戦闘の結果・次手番の確定、重複実行の防止、通常の返答喪失時の自動回収は維持する。

## 検証

- `node tools/cloud/check.mjs`: 既存の戦闘・乱数・再送検証に、自動再送・空HTTPエラー・恒久エラー・退避失敗時の保護を追加。
- `python3 tools/cloud/recovery-browser.py`: 再起動後も同じ要求が失敗する状況を再現し、実際の復旧ボタンで退避しサーバーの記録から再開。
- `python3 tools/cloud/unobtrusive-browser.py`: 通常保存中の操作・自動移動・戦闘待ち・失敗からの再接続。
- `node tools/cloud/database-check.mjs <PGlite>`: 実際のSQLとAPIの再送・確定状態・競合。
- `node tools/cloud/deploy-check.mjs`: 接続設定・権限・公開時の検査。

## HTTP 413の画像を受けた追加調査

新しい画像にはHTTP 413とAPIが発行した問い合わせ番号が表示されている。関数内の2MiB制限で拒否されたことが分かった。回線の状態やオートの通信頻度が直接の原因ではなく、1要求の大きさが原因。端末の実データは取得しておらず、具体的な容量・肥大化したフィールドは未確認。

上限を16MiBへ拡張し、UTF-8のバイト数をストリームで制限する。既存の送信待ちを同じIDで再送できるので、まず「再接続」で復旧する。保存済みの記録からの再開を先に選ぶ必要はない。容量無制限にはしない。共有参照や乱数・戦闘式・保存頻度は変更しない。

DB/API検査に、日本語を含む2MiB超の保存・戦闘・同一ID再送・再開、16MiB超の拒否時の既存記録保持、UTF-8文字の途中で分割された本文の復元を追加した。

## 退避ボタンが進まない画像への対応

「未送信の操作を保管できませんでした」の画像は、復旧ボタンの操作を受け付けた後に退避処理が失敗したことを示す。大きな送信待ちをlocalStorage内でもう1つ複製する実装では、容量の上限に達すると退避できない。退避先をIndexedDBへ切り替える経路を追加し、その書き込みトランザクション完了後にだけ送信待ちを解除する。両方の保管が失敗した時は元要求を残す。エラー文も端末全体の空き容量ではなくブラウザーの保存領域を指すよう変更。ブラウザー検査ではlocalStorageへの退避をQuotaExceededErrorで失敗させ、IndexedDBへの退避と再開を検証する。

## 品の増殖による肥大化を特定

本番の記録を読み取り専用で診断したところ、約2.1MBの記録のうち約2MBが所持品に由来し、同じ種類の消耗品が6,561個あった。クラウド戦闘の応答に共通の袋`inventory`が入っておらず、`applySavePatch`で人業の袋だけが複製され、その後`shareInventory`が別の袋とみなして品を合成していた。結果と次手番の反映を重ねるたびに増える経路がある。2MiB上限の拡張は拒否を回避したが、この増殖を止めるものではなかった。

差分に`inventory`と`formations`を含め、装備・隊・戦利品・編成と同じ参照グラフで送る。旧サーバーへの接続では、全人業が共用する袋を差分の`inventory`として扱う。既に増えた品の自動削除はしない。品の同一内容だけでは、正規に複数所持した品と増殖した品を区別できないため。

参照の検査に、24行動×新旧応答での個数一定、通常保存の比較基準・袋・戦利品・装備・編成の共有を追加。利用者の記録は本番へ書き戻さず、ローカルのAPI・ブラウザーで対象選択から次手番への進行を確認した。調査用の取得は一時公開鍵で暗号化し、鍵はローカルだけに保管した。取得用のワークフロー差分と一時公開鍵は最終変更に含めない。


## ヒール対象選択後の停止（2026-10-30、追加調査）

既存記録へ書き込まず、専用の検証アカウントに6561個の実際の品データを作り、約2.6MBのヒール要求を再現した。旧RPCでは `cloud_commit_slot` が約33秒でHTTP 500、PostgreSQL `57014: canceling statement due to statement timeout`。Edge Functionは503へ変換していた。端末の15秒期限も正常な大容量応答（別の要求で14〜15.3秒）を中断する。

RPC境界を文字列へ変更し、PostgRESTが巨大なJSONを引数として展開・返却する負荷を減らす。同じ内容をDB内でJSONBへ戻し、既存の保存・再送・占有検査を呼ぶ。保存済みデータと端末の未送信要求は変換不要。DBの期限や役割設定は変更しない。新RPCの実行権限はservice_roleだけとする。

本番DBへの新方式の検証では、ヒール確定12.7秒・同じIDの再送12.7秒・読み戻し2.2秒で成功。HP増加、次手番、袋6561個、再送後もrevisionが1のままであることを確認した。検証アカウントは削除済み。利用者の実際のiPhoneでの解消確認は別途必要。

端末の保存API期限を60秒へ延長し、時間切れは自動で繰り返さず復旧画面へ移す。ローカル実API/SQLのブラウザー検証でも20秒遅延したヒールの確定と再起動後の操作を確認する。大きな記録の待ち時間そのものは残る。


公開後の追加確認では、Edge Function経由に限りDB時間切れ57014が残った（問い合わせ番号937d0924-f845-4fe8-9bbe-5ef6f70f43bc）。文字列RPC化だけでは不十分だったため、`cloud_claim_text` / `cloud_commit_text`のPostgREST関数別期限を45秒へ設定する移行202610300003を追加。ほかのAPI・役割の期限や保存内容は変更しない。設定後、公開APIへの同じ約2.6MBのヒール要求が13.6秒、同じIDの再送が10.6秒で成功した。


## 1行動0.5秒以内への変更（2026-10-30）

45秒のDB期限は停止を防ぐ対処で、毎手の通信待ちをなくさない。さらに画面更新時の装備候補判定が袋全体をJSON化し、歩行中も大容量の記録を画面スレッドで組み立てていた。

新サーバーの能力通知により、戦闘は既存の端末Battle・種つき乱数で実行する。行動直前の復旧記録を端末へ保管し、通信は別の列で進める。最新の復旧記録と送信済み要求を分け、再起動時に同じIDの要求を確定後、最新記録を届ける。通常保存は500msで集約する。戦闘式は同じだが、各結果をサーバーが先に計算してから表示する仕様から変わる。端末への保管に失敗した場合は行動を止める。タイトル復帰・公開更新は送信完了を待つ。

参照グラフformat 2は同一スカラー値をテンプレートへまとめ、品の個数・個体性・共有参照を維持する。合成検体6561品で約2.60MB→0.235MB。Workerへ記録準備を移し、装備候補の判定から消耗品の説明を除外し、共有済み袋の再合成と命令板の再測定を省く。旧記録と旧クライアントを読める互換経路を残す。利用者の既存の品は削除しない。

Chromium、390×844、CPUを4倍低速、実際の品6561個、ローカルの実API/SQLで、ヒール対象を実際に押してHP増加と次の入力を確認。通常遅延で439.9ms、保存通信に5秒遅延を追加して431.6ms。歩行は通常遅延で206〜289ms/歩。全端末の上限を保証する測定ではなく、iPhone実機での値は未測定。テストは500ms未満をアサートする。再起動後の袋個数と手番も検査する。

追加のオート戦闘では13区間が207〜423ms/行動。通信未完了で再起動するブラウザー検証でも、最新のHP・乱数位置・次手番・袋6561個の復旧を確認。古い保存の確定で新しい端末記録を消さないこと、端末容量不足の間は行動を進めないことも単体検査に追加。

動きを減らす設定をOFFにした最終確認も、ヒール457.9ms、オート12区間228〜444ms、歩行225〜285msで通過。


## オートが速すぎる・勝利後の保存失敗（2026-10-30）

宝箱のある勝利までブラウザーで再現したところ、`pendingResults.chest.open`に入る操作関数がWorkerのstructured cloneで拒否され、DataCloneErrorとなった。従来のrefSerializeは関数を除外するが、Workerへ渡す前に転送が失敗していた。戦闘中だけの性能検査ではこの経路を通っていなかった。

転送時のDataCloneErrorに限り、関数を除外し共有参照と循環を保った写しを作って再送する。原本の宝箱の操作関数と中身は残す。自動行動は結果表示の間隔を倍速ONで400ms、OFFで500ms以上に調整。端末記録と計算の時間を間隔に含め、通信完了は待たない。手動入力は追加で待たせない。勝利→宝箱戦果の保存→再起動で金貨・Soul・乱数・所持品・宝箱状態を確認し、実際に開錠した後の保存も検査する。
