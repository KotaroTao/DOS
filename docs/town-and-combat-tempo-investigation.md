# 街・設定と戦闘テンポの調査 (2026-10-29)

## 戦闘で遅くなる原因と修正

従来は一行動につき「選択をsave」「battleで結果を確定」「advanceで次の手番へ」の3要求を直列に待っていた。各要求には認証・記録の取得・DBへの確定があり、回線の遅延が積み重なる。さらにオートの作戦決定後90ms、手番の合間約68ms、敵の予備待機約117msなどを通信とは別に足していた。サーバー確定済みの次手番でも、演出の片付けによる差で再保存が発生した。

- 対応サーバーでは `turn` で選択保存・結果・次手番を一度に確定する。結果と次手番は別々にシリアライズし、画面では一手の演出後に次手番を反映する。
- 次手番の受領まで途中の状態を保存しない。演出中に終了しても、保存済みの次手番から再開し、行動をやり直さない。
- 旧サーバーはclaimの対応フラグが無いため従来の要求へ戻す。既存クライアントのbattle／advanceも受け付ける。SQLの変更は不要。
- オートの作戦決定後と手番の追加待機を0msにし、終了の間は100msに短縮。クラウドでは敵・行動不能の通信前に予備待機を足さない。踏み込み、多段ヒット、被弾、強化弱体の演出は残す。
- 次手番は保存済みなので、演出を片付けただけでは全記録を再送しない。装備・技・乱数・戦闘の計算式は変更しない。

実Edge FunctionとSQLを使い、ブラウザで各要求に250msの遅延を加えて8行動ずつ測定した。行動間隔の平均は従来の通信方式1,076msから一括確定565msへ約48%短縮。一括側の測定要求は開始時のsaveと8回のturnで、行動ごとのsave／battle／advanceが無いことも確認した。これはローカル検証環境の測定であり、本番の端末・回線・サーバーの負荷により時間は変わる。結果確定のための通信1回は残る。

## 街・設定などの関連不具合

前回の通常保存中の入力封鎖の修正は街にも適用されていた。一方、次の問題が残っていた。

1. タイトル復帰／公開更新では、最後の保存を作った後も背面の操作ができ、保存対象と再読込の間に新しい変更が入る余地があった。`cloudPrepareReload` で入力を封じてから保存を作り、保存と送信待ちの完了後に読み直す。二重要求も受けない。
2. アカウント管理は送信待ちを待つ間、何も表示せず、別画面へ移った後で管理画面が出る可能性があった。押した時点で遷移中の表示と入力停止を行う。
3. 左下の灯／全画面の画像エラーの再試行は `location.reload()` を直接呼び、進行中の保存完了を待たなかった。起動前を除き、タイトル復帰と同じ保存処理へつなぐ。保存できない場合は読み直さない。
4. 手ほどきの指定外入力を止める処理が、更新・通信復旧・画像再取得・規約の操作まで遮っていた。これらのシステム操作は手ほどきより優先する。
