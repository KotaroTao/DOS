## 分割の基本方針
1. **データとロジックを分ける。** データは「層ごと・職ごとに1ファイル」、ロジックは「機能ごとの縦割り」。`src/jobkit/<job>.js` が成功例。
2. **依存の向きを一方向に固定する** (今の「`ui/` は `game.js` を import しない」の拡張):
   ```
   データ (arts, catalog, jobkit) → 純粋なルール (combat, souls, loot計算)
     → 状態を触るシステム (save, battle, board, town…) → game.js (起動・ループ・結線のみ)
   ```
   下の層から上の層は import しない。
3. **`G` を `src/core/state.js` へ** (`export const G`)。
4. **相互呼び出しの中心 (`endBattle`・`descend`・`returnToTown` など) は最後まで `game.js` に残す。** 先に周辺 (葉) から切り出して、循環 import と読み込み順の問題 (TDZ) を避ける。

### いまの状況 (この追補を書いた時点)
- **尺度の統一は半分進んでいる (#489)。** 迷宮ごとに推奨Lv (`world.js` の `lv` / `lvTo`) を直接書き、報酬 (✦Soul・金貨 = `src/levelcurve.js` の `refSoul` / `refGold`)・落とし物の帯 (`lootBand`)・魂の強化費用 (`trainCost`)・魂の残火 (`emberMul`) は推奨Lv から決まる。
  ただし**敵の強さだけは旧来の n の物差しのまま**で、`lvStrength` = lvPow(推奨Lv) ÷ lvPow(n の物差しの Lv) を掛けて推奨Lv へ写している (各迷宮の `tune` が n の物差しの隊で合わせてあるため)。
- #487 で親しさの段は「王に報告した章の迷宮の数 `BOND_REPORTED = [0,1,2,5,9,13]`」で決まるようになった。

### #487 (イレーヌの親しさ) への提案
1. **【直すべき】段が迷宮を回る順でずれる。** `[0,1,2,5,9,13]` は「第1章の5本をすべて報告してから第2章へ」を前提にしているが、黒水の取水口 (w04, `unlock: { story: "w02_sigil" }`) は鎖の垂れる坑口 (w05, `unlock: { treasury: 3 }`) と独立で、第2章 (w06) は w05 の報告だけで開く。
   w04 を後回しにすると、第1章の結びで報告4本 (3段目は第2章に入ってから)、第2章の結びで8本 (4段目は第3章の最初の報告) になる。
   → **`段 = min(2, 報告数) + 結び (story.js CHAPTERS[].finale) を報告した章の数` (上限5)** に変える。迷宮を足しても並べ替えても詰め直し不要で、「どの順で回っても筋が通るように書く」物語の決まりにも合う。変更は `src/ui/irene.js` の `bondOf` 周りの数行。
2. **【任意】第4章からの話題を書きやすく。** 段は第3章の結びで最大 (以降は `LINES` で深める方針) なので、`ctxNow()` に「結びを迎えた章の数」`c.chapters` を足し、`when: (c) => c.chapters >= 3` のように章ごとの台詞を書けるようにする (1 と同じ値を使い回す)。
3. 融合の案内文 (`FEATURE_AT.fusion` をそのまま表示) は問題なし。ほかに解放の数を手書きしている文は見つからなかった。

### この計画書 (#488) への提案
1. **尺度の統一の残り半分は、手触りを変えずに済ませられる。** 「旧来の n の強さ (`cfg.enemyScale` × 階の上がり幅) ÷ lvPow(n の物差しの Lv)」を迷宮ごとの `tune` に畳み込めば、敵の強さ = lvPow(推奨Lv) × `tune` × 魔物のランクの相対値 になり、挙動は変わらない (テストプレイのやり直し不要)。これで地図の迷宮から `generateDungeon(n)`・`baselineLv`・`LV_EST`・`naturalLevelRaw` を外せる。
   残す尺度もはっきり決める: **推奨Lv = 難しさの唯一の物差し** / 装備の隠しLv・R = 推奨Lv から導く (`lootBand`) / layer = 景色・顔ぶれのまとまり (難しさには使わない) / 魔物のランク = 顔ぶれの中の相対的な強さ / `cfg.rank` = 消す。「6種を1種に」より「難しさは1本、ほかは役割を限定」と書いたほうが作業の範囲が明確。
2. **安全網に「調整の自動検証」を入れる (計画書に抜けている)。** 弱みに「調整の自動検証が無い」とあるのに進め方に無い。#489 で使った検査 = Playwright で本物の `game.js` を読み込み (テスト時だけ読み込みを差し替えて `window.__T` に内部関数を出す)、全迷宮の1階と最下階で「1戦の✦ ÷ 基準 (`refSoul`)」と「被ダメ (隊HP比): 推奨Lv の隊 × Lv 補正込みの敵 ↔ n の物差しの隊 × 補正なしの敵」を測る — を `tools/check/` に置き、許容幅を決めておけば、迷宮・敵・職を足すたびにバランスの崩れを機械で見つけられる。
3. **CI は2段に分ける。** 公開を止める速い検査 (`node --check`・読み込み時の検証・`sw.js` の `ASSETS` の書き漏れ) と、別の流れの重い検査 (Chromium の通しテスト・バランス検査)。
4. **`sw.js` の `ASSETS` を手で書かない。** 公開の CI で import をたどって自動生成するか、最初の画面の分だけ先に読み込み残りは使った時に保存する方式に変える。ファイルの分割 (第5段) で数が何倍にもなるので、それより前に必要。
5. **絵のデータは JS の配列ではなく画像ファイルに。** `schema.js` の `ARTS` (約1.6MB) と `jobart.js` (約720KB) は分割しても JS の大きさは変わらない。1ドット = 1画素の PNG にして読み込み時に今の `{palette, art}` の形へ戻せば、配布サイズが数分の1になり、`jobart` (ドット絵) と `jobphotos` (webp) の二重の仕組みも1つになる (#477〜#481 で戦士・竜騎士の絵が行き来したのもこの二重構造のせい)。読み込みが非同期になるので起動処理に手が入る。第4段で選ぶ価値がある。
6. **セーブの変換の仕組みは今から。** 「公開直前に固める」だと仕様変更のたびにテストがやり直しになる。保存データに版数を持たせて変換を順に当てる最小限の仕組み (数十行) を第1段に入れる。
7. **`CLAUDE.md` の分割を早める。** 毎回の作業で丸ごと読まれ、非常に長い。モジュールごとの詳しい説明を `docs/` へ移すのはコードに触れずにすぐできるので、第1段と同時に進める。
8. **解放・段階を「迷宮の数」で決めている箇所も統一の対象に入れる。** 機能の解放 `FEATURE_AT` (報告数 2・3・4・5・7・11)・親しさ (報告数 0・1・2・5・9・13 → #487 の提案1で章の結びへ)・`CHAPTERS[].finale` (結びの迷宮を直接指定 = いちばん確かな物差し)。迷宮を100本まで増やす前に「章・特定の迷宮で決める」方針にしておくと、足すたびに数字を詰め直さずに済む。
9. **細かい点。** 範囲は行番号ではなく関数名・見出しで書く (行番号は数日で古くなる)。`game.js` を分ける境目には既存の `bindGame` (ui との結線) の形を使うと循環 import を避けやすい。README の現状との食い違いはすぐ直せる。
