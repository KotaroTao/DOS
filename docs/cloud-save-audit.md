# クラウド保存の総点検（2026-10-30）

対象: PR #1342までのmainを基準に、保存・再開・戦闘・復旧・認証・公開更新を点検した。検査結果は8ロジック＋20ブラウザ、計28/28通過。後続のmain（PR #1343・#1344）も取り込み、8ロジックと起動復旧・終了保全・ゲスト登録の3ブラウザ検査を再確認済み。

## 修正した問題

| 問題 | 再現・影響 | 修正 |
| --- | --- | --- |
| 終了直前の保存準備が完了しない | Workerを停止させ、金貨を1234・品を1つ増やして画面を閉じると、再開時に変更が戻る。修正前は金貨2284→1050、品1→0を確認 | `visibilitychange`・`beforeunload`・`pagehide`で最新地点を同期保管。次回起動で通常の再送列へ回収。古い準備や応答で削除しない |
| 起動途中の入力制限の早期解除 | 送信待ちの保存が終わった時点で幕が消え、最新記録の再取得が続いていても操作できる。遅延を注入して再現 | 接続完了前は通常保存の完了通知で幕を消さない。最新記録の取得完了後に解除 |
| Workerの生成拒否で保存不能 | Workerという名前が存在しても、生成時にSecurityErrorが出る条件を注入すると記録を作れない | 生成拒否時は同期シリアライズへ戻す。品の個体・循環・共有参照を保持 |

途中で疑った「文字列の復旧記録の本文欠落」は、通常の保存経路では既に送信用の形式へ変換されていた。通常操作で発生する不具合としては数えていない。文字列を元に作った復旧記録の新旧形式・再送順序の検査は追加した。

## 検査範囲

`tools/cloud/audit.py` は8ロジック検査と20ブラウザ検査を順に実行し、各ログと結果JSONを保存する。APIの検査はAuthだけを模擬し、PGlite上の実SQLとEdge Functionを通す。

| 分野 | 確認内容 |
| --- | --- |
| 保存形式 | 新旧の参照グラフ、同一品・袋・装備・戦利品の共有参照、循環、操作関数の除外、圧縮形式 |
| 保存順序 | 連続保存の集約、旧要求→最新の端末記録の回収、要求の重複実行防止、古い応答による削除防止 |
| SQL・API | 更新番号・占有期限・別端末競合・権限・接続元・未認証の拒否・16MiB上限 |
| 戦闘 | 300条件の結果・乱数・次手番、新旧サーバー方式、死亡・道具・窃盗・レベルドレイン、再起動 |
| 大容量 | 6561品の共有袋、未確定通信を残した強制再起動、最新HP・乱数・次手番、低速CPU時の操作 |
| 復旧 | タイムアウト、HTTP失敗、再接続、退避、保存領域不足、IndexedDBへの退避、旧記録の保持 |
| 認証 | ゲスト開始、同意、同一IDへの登録、メール確認の模擬、認証更新失敗時の保全、再開、退会 |
| 画面 | 低速保存中の施設操作、入力待機、オート移動、短い効果、戦果と宝箱、保存後のタイトル復帰 |
| 保存の保護 | 別タブ・古い上書き・破損記録・退避と復旧、削除取消・新規開始、更新前の保存 |

現行方式に合わなくなっていた検査も修正した。互換戦闘の比較は`backgroundBattle`を明示して無効化し、非同期準備を100msで完了したと決めつけず送信開始を待つ。移動1倍の問いの検査、非表示にした起動待機文、タイトルの文節区切り・新規開始名も現行仕様に合わせた。

## 本番での確認

公開接続先に対し、データを更新しない要求で、許可したOriginのOPTIONSが204、許可外が403、未認証のPOSTが401となることを確認した。プレイヤーの記録を読み書きする実アカウントでの操作は行っていない。

## 再発防止と制限

関連コードのPRでは、GitHub Actionsの`Cloud save regression checks`が8ロジック検査と構文検査を実行する。ブラウザ検査は上述の一括コマンドで実行できる。ゲームへの依存やビルド工程は追加しない。

実SMTPからのメール到着・実機Safari/PWA・本番DBのバックアップ復元は、この環境では未検証。OSが終了イベントを一切通知せずにプロセスを破棄した場合は、最後に端末へ保管できた地点までが復旧対象となる。通信中に別端末へ移る場合も、保存済み地点が基準となる。
