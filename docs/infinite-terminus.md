# 無限迷宮の終点の仕組み (設計)

状態: **設計のみ・未実装** (2026-11 ユーザーと決定)。
このリポジトリは公開されている。そのため、この文書には**終点の階・その値の意味・到達した時の中身を一切書かない**。書くのは、それらを隠したまま動かすための仕組みだけ。

関連: `docs/item-generations.md` (装備の世代と深部の解禁)。終点の扱いはこの文書を優先する。

## 1. 方針

1. **端末のゲームには上限を持たせない**。コードの上では、無限迷宮はどこまでも降りられる作りにする。上限の数字がコードに存在しないので、解析しても見つからない。
2. **終点の判定と、到達した時の処理・中身は、すべてサーバー側で行う**。
3. **到達は、サーバーで確かめてから認める**。改造そのものは防げない前提で、偽の到達を見抜いて認めない。

## 2. 秘密にするものと置き場所

| 秘密 | 置き場所 |
|---|---|
| 終点の階 | サーバーの秘密の環境変数 (Supabase の Edge Function の secret。GitHub の Secret から登録)。ユーザーが別に控える |
| 終点の値の意味 | ユーザーだけが知る |
| 到達した時の中身 (文・演出・画像) | 公開リポジトリの外 (サーバーのストレージなど)。到達を認めた者にだけ渡す |
| 到達の検査の基準 (§5 の閾値) | サーバーの秘密の設定 |

### 2-1. 運用の約束

- 上の秘密は、**文書・CLAUDE.md・AGENTS.md・コードのコメント・コミットの文・PR の説明・CI のログ・テストの名前・画面・心得・勲章**のどこにも書かない。
- Claude・Codex の作業の記録には残らないので、実装の時にユーザーから直接受け取る。受け取った値は秘密の環境変数の登録にだけ使い、ファイルに書かない。
- 秘密の環境変数の名前は、値や意味を連想させない一般的な名前にする。
- CI・配置のスクリプトは、秘密の値をログに出さない (GitHub Actions のマスクに任せず、出力そのものをしない)。
- 中身の確認は、公開版とは別の非公開の環境で行う。値と中身を知る人は最小限にする。

## 3. 端末側

- 深部の解禁後の上限 (`src/progression.js` の `depthLimit`) は「上限なし」にする。今ある仮の上限の数字は消す。
- 降下・飛び階・落下・魂の記憶からの開始は、深部の解禁後は端末では止めない。止めるのはサーバーの印だけ (§4)。
- 終点を前提にした大きさの表・配列・段を作らない。勲章の段は今のまま刻みで延々と続ける。装備の世代の数字・推奨Lv・値段の表示は、桁が増えても崩れないようにする。
- 数値の安全性の検査では、終点の値と無関係に決めた複数の桁の値 (例: 1万・10万・100万・1000万階) で式が壊れないことを確かめる。検査の値から終点の大きさを推測できない形にする。
- オフライン (ローカル保存) では終点は判定されない。終点の到達はクラウド保存が前提。

## 4. サーバー側

1. 保存API (`supabase/functions/game-save`) が無限迷宮の階の移動を含む保存を受けた時、秘密の値と比べる。比べる処理以外で値を使わない。
2. 終点に着いた保存では、到達の記録を作る (到達時刻・累計プレイ時間・階の移動の記録の要約・隊の要約)。状態は「審査待ち」にする。
3. その保存の応答に「これ以上は降りられない」印を含める。端末はこの印でだけ降下を止め、待機の表示をする。印には数字を含めない。
4. 到達した時の中身は、審査を通った後に、その者にだけサーバーから渡す (§5)。中身を端末のコードや公開の配置物に含めない。
5. 終点より深い階の保存が届いたら、改造の疑いとして記録し、到達とは認めない。

## 5. 到達の確認 (改造・解析への対策)

改造そのものは防げない。端末で動くゲームは書き換えられる。そのため、到達をサーバーで確かめる。

| 段 | 内容 | 採否 |
|---|---|---|
| ① 申請と人の目による審査 | 到達を自動で認めず、記録を確認してから認める | 採る |
| ② 妥当性の自動検査 | サーバーに残した階の移動の記録 (時刻) から、1階あたりの時間・累計プレイ時間・階の飛び方 (魂の記憶からの再開や落下など正規の手段だけか) を確かめる。基準はサーバーの秘密の設定 | 採る |
| ③ 戦闘の台帳 | 深い階の戦闘を、選択をサーバーで記録・再計算する台帳 (B方式、`docs/battle-ledger-performance.md`) に乗せ、検証済みの戦闘の数と階の進み方が合うかを見る。どの深さから乗せるかはサーバーの秘密の設定 | 採る |
| ④ 全体の再現 | 種つき乱数 (`src/rng.js`) と操作の記録から、到達までの全プレイをサーバーで再現して確かめる。最も確実だが、すべての処理を再現できるようにする大きな作業になる | 今は採らない。到達者が現れそうになってから検討 |

- コードを読みにくくする加工 (難読化) はしない。守る力がなく、ビルドの工程を持たない方針とも合わない。
- ②のため、階の移動の記録をサーバーに残す。1回の移動につき時刻と階だけの小さな記録にし、容量を見積もってから実装する。

## 6. 実装の順

1. 端末の上限をなくし、サーバーの印で止める仕組み (§3・§4-3)。
2. 階の移動の記録をサーバーに残す (§5-②)。
3. 到達の記録と審査待ちの状態 (§4-2)。
4. 深い階の戦闘を台帳に乗せる (§5-③)。
5. 到達した時の中身を、公開リポジトリの外で作って配る (§4-4)。

各段はユーザーの了解を取って進める。
