# 迷宮・戦闘の進行停止の調査 (2026-10-29)

## 原因と影響

1. `CloudSaveClient` は保存・戦闘・占有延長を同じ busy で扱っていた。`uiBlocked` がこれを参照するため、通常保存のたびに盤面操作・マス開示・自動歩行・戦闘の開始が通信の往復待ちになった。街や各施設の `uiBlocked` を使う操作も同じ影響を受ける。
2. `autoMoveTick` は `uiBlocked` を「選択を挟んだ」と記録していた。1歩終わりの保存が続いているだけで選択中断になり、保存が終わるとオートが切れる。画像準備の一時待機でも同じ誤判定が起きる。
3. 保存要求はすべて直列送信される。入力を開放するだけでは低速回線で古い記録が積み上がり、次の戦闘や終了保存を待たせるため、未送信の連続保存だけ最新に集約した。送信開始済みの要求と戦闘前後の境界は変更しない。
4. 戦闘応答を受けるたびに保存比較の基準を破棄していた。サーバーに確定済みの状態まで次の autosave で再送し、その完了が次の手番に重なる。送信済みの記録へ応答の差分を反映して比較基準にする。端末の未送信の変更はこの基準に含めず、変更があれば従来通り送る。

## 維持する動作

戦闘結果はサーバーの確定を待ってから表示するため、その通信時間は残る。通信失敗・競合・ログイン中は操作を止める。実際の問い・シート・設定を挟んだオート移動の解除、負傷時の停止も維持する。再送時の要求ID・内容・版番号、共有参照、戦闘の乱数と一度だけの実行は変更しない。API・SQLの更新は不要。

## 検証

- `node tools/cloud/check.mjs`: 30種の戦闘再開、死亡・損失の確定、共有参照、返答喪失の再送、送信待ち回収、保存集約と戦闘境界、版番号、戦闘応答の保存比較。
- `python3 tools/cloud/unobtrusive-browser.py` (localhost:8001): 低速保存中の入力、戦闘待ち、占有延長、通信失敗からの復旧。実際の迷宮画面で5秒の保存待ちの間に3マス以上進み、オートが継続すること。画像待機で解除せず、実際の問いの後には解除すること。
- 全 `src/*.js` の `node --check` と `git diff --check`。
- `node tools/cloud/deploy-check.mjs`: 公開接続設定・認証・権限の既存検査 (外部サービスは模擬)。
