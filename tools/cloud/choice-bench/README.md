# B方式の選択記録の速度を実サーバーで比べる

B方式を採用する前の試作。本編の保存方式・本番のgame-save関数・本番アカウントのセーブを変更しない。別のschema・RPC・Edge Functionと、一時的な試験アカウントだけを作り、終了時に削除する。試験アカウントの作成とログインリンク生成でメールは送らない。

比較するもの:

- `current`: 現在公開中のgame-saveへ、小さな戦闘命令を送る。合成した200品/2,000品の記録を試験アカウントに保存し、サーバーで結果・セーブ全体が確定するまでを測る。
- `B_auth_api`: 現在と同様にEdge Functionから認証APIへ照会し、小さな命令表への追記を1回のRPCで確定する。戦闘計算とセーブ全体の読み書きは行わない。
- `B_db_jwt`: PostgRESTのJWT検証・`auth.uid()`で所有者を確認し、同じ追記RPCを直接呼ぶ。認証APIへの追加照会がない比較であり、失効・退会等の運用を含む採用決定ではない。

各方式で3回のウォームアップ後に20回（または40回）、順序を交互に変えて直列測定する。中央値・平均・p95・最大・本文バイト数と、BのEdge内の認証API/DB往復の時間を残す。`edge_region=database`はEdgeへの要求に`x-region`を付け、DBと同じリージョンを指定する。Bの関数が返す実行リージョンで指定の適用も確認する。初回の値も別に残すが、初回が必ずコールドスタートとは限らない。現在方式の結果が同じコードによる独立計算と一致しなければ停止する。

**この測定はGitHubの検証環境からの実サーバーへの応答時間。利用者の端末・回線、演出を含む体感速度、B方式の戦闘開始・終了検証・全体保存・同時接続の容量は測っていない。** p95は少数標本の参考値。Bの試作は記録順・所有者・再送・変更拒否を備えるが、戦闘の合法性や報酬検証は実装していない。速度が速くても、それだけでBを本番採用できるわけではない。

実行:

```bash
node tools/cloud/choice-bench/check.mjs /tmp/dos-cloud-check/node_modules/@electric-sql/pglite/dist/index.js
gh workflow run cloud-save-check.yml --ref codex/choice-speed-probe -f choice_benchmark=true -f samples=20 -f edge_region=auto
```

Actionsの`choice-speed-benchmark`成果物に`setup.json`・`results.json`・`cleanup.json`が入る。認証情報・JWT・メールアドレスは成果物に含めない。結果と片付けの成功を両方確認する。通常の完了・ステップ失敗時は`always()`の片付けを行うが、runnerの強制停止等で実行されない場合は、同じ実行IDの試験リソースの削除が必要。計測本体は6分、個々の測定は15秒で打ち切り、通常の失敗時に片付けへ進む。

SQL試作の命令は1つ2KiBまで、1試験256手まで、1時間で失効する。RPCの開始はservice_roleだけに許可し、クライアントは自分の試験にだけ追記できる。試験schemaはAPIへ公開せず、表への直接アクセスを許可しない。

## 実測結果（2026-11-01 UTC）

DBは東京 `ap-northeast-1`。各行は「中央値 / p95」、単位はms。記録は試験用の200品（87,795 bytes）、2,000品（834,264 bytes）。利用者の実セーブではない。

東京指定、各方式・各サイズ40回（別にウォームアップ3回）:

| 記録 | 現在方式 | B・認証API維持 | B・DBのJWT検証 |
|---|---:|---:|---:|
| 約88KB | 397 / 899 | 255 / 366 | 166 / 179 |
| 約834KB | 1,068 / 1,285 | 257 / 340 | 167 / 174 |

[実行41256925656](https://github.com/KotaroTao/DOS/actions/runs/41256925656)。Edgeの実行リージョンが東京であることをレスポンスで確認。B・認証API維持の関数内の認証API・DB往復はそれぞれ中央値約29〜37ms。88KBで約997msの応答も1件あり、その関数内処理は約258msで、残りはこの計測では接続・gateway・起動待ち等に分解できない。

自動配置、各方式・各サイズ20回（別にウォームアップ3回）:

| 記録 | 現在方式 | B・認証API維持 | B・DBのJWT検証 |
|---|---:|---:|---:|
| 約88KB | 594 / 1,381 | 310 / 598 | 123 / 341 |
| 約834KB | 1,639 / 2,822 | 325 / 599 | 129 / 280 |

[実行41256536277](https://github.com/KotaroTao/DOS/actions/runs/41256536277)。この実行ではEdgeは米西海岸 `us-west-1`、DBは東京。Bの関数内の認証API・DB往復はそれぞれ中央値約136〜144ms。2つの実行はrunnerやネットワーク条件が同一とは限らないため、**実行をまたぐ数値差を、配置だけの改善率としては扱わない**。

同じ実行内で見ると、Bの選択記録は現在方式より短く、セーブ全体を大きくしても応答時間がほぼ増えなかった。Bの利点を支持する結果。ただし完成したBのゲーム体験・終了検証・同時接続の負荷は未測定で、直接JWT検証の採用には失効等の別の評価が必要。

両実行とも、専用Edge Function・試験アカウント・専用schemaの削除が成功。ゲームの方式・本番のgame-save・mainブランチは変更していない。raw標本と片付けの結果は `results/` に保存している。

## 利用者の端末での計測・戦闘試遊

設定の「自動化・データ」→「B方式の通信・戦闘試遊」で別画面を開く（`choice-trial.html`）。先に本編のタイトルから接続しておく。専用の試遊RPCは `202611010001_choice_trial.sql` にあり、公開時の `supabase/deploy.mjs --prepare` で追加される。

1. **通信を20回計測**: 自分の端末・回線で小さな命令の追記と確定通知を直列に測る。ウォームアップを除外せず20回すべてを集計する。開始の通信も別に残す。
2. **戦闘試遊を比較**: 「確定通知を待って着弾」と「構えと通信を重ねて着弾」をそれぞれ開く。同じ固定乱数・Lv20の隊と専用の敵で既存の攻撃・技・着弾演出を使う。どちらも通知後に初めてBattleを計算する。重ねる方は通知前に肖像を少し持ち上げ、光らせるだけ。通知後に足す固定待ちはない。構えが早く始まっても通信時間そのものの短縮ではない。敵・行動不能の強制手番は端末で進める。
3. **B計測を書き出す**: `dos-choice-trial.json` に、版・画面サイズ・接続の種別と推定RTT（ブラウザが提供する場合）・各通信の本文バイト数/時間/成功状況・各選択から構え/確定通知/着弾処理開始までの時間・再接続回数・中央値/p95/最大を残す。着弾の値は演出処理の呼び出し時点で、ディスプレイへの表示完了の実測ではない。本文量にはHTTPヘッダー・TLSを含めない。認証情報・ユーザーID・命令ID・本編の記録本文は出力しない。計測結果は画面を閉じる前に書き出す。

本編の保存と混ざらない既存の `testDungeon` 試遊を使う。本編の隊を読み込まず、勝敗から報酬処理へも進めない。試遊中は本編の保存APIを呼ばない。ログイン情報は読み取るだけで更新しない。期限切れは本編のタイトルで再接続する。通信に失敗した命令は同じID・本文で再接続し、別の選択へ変えない。端末保管ができない場合は結果へ進めない。

試遊は1時間12回・同時3件・各256手まで。自分の試遊だけ操作でき、終了時は削除する。放置分は1時間で無効になり、次の開始時に最大100件ずつ削除する。試遊を再開して本編を進める仕組みではなく、リロード後の継続・戦闘開始状態のサーバー確定・戦闘終了時のリプレイ検証・報酬確定は含まない。**これはB方式の本番実装ではなく、選択記録の時間と体感を比較するための試遊である。**

検証:

```bash
node tools/cloud/choice-bench/trial-check.mjs /tmp/dos-cloud-check/node_modules/@electric-sql/pglite/dist/index.js
python3 -m http.server 8000
# 別の端末操作で実行
python3 tools/cloud/choice-bench/trial-browser.py
```

ブラウザ検査は350/900msの応答待ちと返答消失を作って、確定前のHP・MP・乱数不変、構え、既存の着弾、同一ID再送、本編保存不変、JSONを確認する。この人工待ちを含む戦闘レポートは速度の実測値には使わない。CIは `--stub-art` で画像だけ置き換え、ローカルでは本物の画像も確認する。手動の実サーバー比較は公開用と同じSQLを専用名で作り、試験用ログインだけでブラウザ検査・20回計測を実行し、終了時に専用schema/RPC/アカウントを削除する。成果物の `browser/measure.json` はGitHub runner内の操作用ブラウザからの参考値であり、利用者の端末・回線の値ではない。
